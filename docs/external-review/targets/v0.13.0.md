## Technical challenge interfaces

Place synthetic challenge data in a new directory under `review-inputs/` inside
the isolated source root. Preserve the original inputs and controlled changes.
For a dataset at `review-inputs/case-001`, use:

```text
python scripts/validate_phase1.py review-inputs/case-001
python scripts/run_monthly_monitoring.py review-inputs/case-001 --evidence-root review-output/case-001
python scripts/run_adverse_action_reason_benchmark.py review-inputs/case-001 --output-dir review-output/case-001-benchmark
```

Preserve validation errors and run later stages only where meaningful. The
monthly command reports the generated run directory. The benchmark adds
supplemental checks but retains the curated suite's fixed expectation of 21
exception types. A clean or small custom case may return exit code 1 because
it lacks that entire suite. Inspect `missing_expected_exception_types` and
findings for the target decision; distinguish that condition from an execution
failure. Aggregate success is not proof that the target defect was detected.

## Disclosed target limitations

These are maintainer observations and regression evidence, not independent
review findings. Corrections are limited to the declared contracts and tested
conditions; reviewers may challenge them and identify further defects.

| ID | Behavior or limitation | Review treatment |
| --- | --- | --- |
| KI-01 | Corrected for the declared principal-driver scope: QA reports unmapped and omitted principal drivers, including mixed mapped/unmapped cases. | Generation can still emit diagnostic candidates; content export blocks unresolved findings. Challenge both defect and clean cases. |
| KI-02 | Corrected: mapping/template lifecycle checks use the recorded UTC decision timestamp, with inclusive activation and exclusive retirement. | Test differing application/decision dates and exact boundaries. Invalid timestamps are rejected. |
| KI-03 | Repository validation still requires Git metadata. | Use the scoped archive-compatible commands; do not infer full archive portability. |
| KI-04 | Deep Windows paths remain an environment constraint. | Use short paths and record failures; a workaround is not general portability evidence. |
| KI-05 | Aggregate benchmark acceptance remains exception-type coverage, not per-case accuracy or false-alarm performance. | Inspect decision-level outcomes; regression tests do not supply real-world reference labels. |
| KI-06 | Content checks use editable declared reviews and a trusted local process, clock, and one writer per destination. | No authenticated approval, revocation/replay protection, coordinated writes, operational authorization, or notice delivery is provided. |

The curated benchmark retains intentional defective records and expects 21
exception types. It is not a passing content review. A populated reason list
or successful run does not authorize use. The [content contract](../../adverse-action-reason-run-kit/REASON_CONTENT_REVIEW.md)
documents blocking checks, review migration, and the deferred approval system.
Timestamp inputs must use calendar-valid `YYYY-MM-DDTHH:MM:SSZ` values; suppliers
must normalize offsets explicitly. Do not substitute an application date.

Prepared pack provenance identifies the actual captured source and input bytes;
it is not a claim that the pack was generated after tagging this release.
Record fresh executions separately. Preserve original findings and retests;
neither review nor retest requires another release or tag.
